# vaultdb-orm

A typed ORM-style layer over [`vaultdb-core`](../vaultdb-core). Declare
a Rust struct that represents a kind of note in your vault and query
it like a database row — including joins via the wiki-link graph.

```rust
use serde::{Deserialize, Serialize};
use vaultdb_orm::{Note, Query, Vault};

#[derive(Debug, Clone, Serialize, Deserialize, Note)]
#[note(folder = "3-Notes", filter = "tags contains type/paper")]
struct Paper {
    #[serde(rename = "_name")]
    title: String,
    year: i32,
    tags: Vec<String>,
    #[serde(default)]
    rating: Option<String>,
}

let vault = Vault::discover(std::path::Path::new("."))?;

// Compile-checked filter — typos on field names won't build.
let papers: Vec<Paper> = Query::<Paper>::new(&vault)
    .filter(Paper::year().ge(2024) & Paper::tags().contains("topic/llm"))
    .order_by(vaultdb_orm::SortKey { field: "year".into(), descending: true })
    .limit(10)
    .fetch()?;
```

## What it gives you

| Capability                              | How                                       |
|-----------------------------------------|-------------------------------------------|
| Typed records                           | `#[derive(Note)]` + serde                 |
| Discriminator filter applied implicitly | `#[note(filter = "tags contains type/paper")]` |
| Typed field accessors                   | `Paper::year()`, `Paper::tags()`, …       |
| Boolean composition                     | `a & b`, `a \| b`, `!a` over `Expr`       |
| Joins via wiki-link graph               | `Paper::cites().any(Paper::tags().contains("topic/ai"))` |
| Bulk mutations                          | `Query::update().set(…).plan() / .execute()` |
| Safety on bulk updates                  | `Query::update()` rejects without a `.filter(…)` |

## Model shape

The macro reads two struct-level keys and two field-level keys:

```rust
#[derive(Note)]
#[note(
    folder = "3-Notes",                          // required
    filter = "tags contains type/paper",         // optional discriminator
)]
struct Paper {
    #[serde(rename = "_name")]                   // map a struct field to a virtual field
    title: String,

    year: i32,
    tags: Vec<String>,

    #[serde(default, skip)]
    #[note(wikilink)]                            // outgoing relation accessor
    cites: Vec<String>,

    #[serde(default, skip)]
    #[note(backlink)]                            // incoming relation accessor
    cited_by: Vec<String>,
}
```

Generated by the macro:

- `impl Note for Paper { const FOLDER = "3-Notes"; fn discriminator() { … } }`
- `Paper::title() -> FieldRef` bound to the frontmatter key `_name`
- `Paper::year() -> FieldRef` bound to `year`
- `Paper::tags() -> FieldRef` bound to `tags`
- `Paper::cites() -> RelationRef` (outgoing — uses `Expr::LinksTo`)
- `Paper::cited_by() -> RelationRef` (incoming — uses `Expr::LinkedFrom`)

`#[note(wikilink)]` / `#[note(backlink)]` mark relation accessors;
the macro skips emitting a `FieldRef` for those fields. The fields
themselves are not auto-materialised in v1 — the relation is for
filtering, not for traversal-on-load.

## Examples

Five runnable examples ship with the crate:

```bash
cargo run -p vaultdb-orm --example paper_hand     # hand-written Note impl
cargo run -p vaultdb-orm --example paper_derive   # same, via #[derive(Note)]
cargo run -p vaultdb-orm --example paper_typed    # typed field accessor DSL
cargo run -p vaultdb-orm --example paper_mutate   # bulk update plan/execute
cargo run -p vaultdb-orm --example paper_graph    # joins via the wiki-link graph
cargo run -p vaultdb-orm --example tauri_shape    # Tauri integration shape
```

## Tauri integration

The cleanest Tauri pattern: each model derives `specta::Type` alongside
`Note`, each command is `#[specta::specta] async fn`, and `tauri-specta`
generates the TypeScript bindings.

```rust
// Cargo.toml
[dependencies]
vaultdb-orm  = "1"
tauri        = "2"
specta       = "2"
tauri-specta = "2"
serde        = { version = "1", features = ["derive"] }

// models.rs
#[derive(Serialize, Deserialize, Note, specta::Type)]
#[note(folder = "3-Notes", filter = "tags contains type/paper")]
pub struct Paper { /* ... */ }

// state.rs — long-lived state held by Tauri.
pub struct VaultState {
    pub vault: Vault,
    pub plans: Mutex<HashMap<String, ParkedPlan>>,
}

// commands.rs
#[tauri::command]
#[specta::specta]
pub async fn list_papers(
    state: tauri::State<'_, VaultState>,
    filter: PaperFilter,
) -> Result<Vec<Paper>, String> {
    let mut q = Query::<Paper>::new(&state.vault);
    if let Some(y) = filter.year_min { q = q.filter(Paper::year().ge(y)); }
    /* … */
    q.fetch().map_err(|e| e.to_string())
}
```

Frontend (auto-generated by `tauri-specta`):

```typescript
import { commands, Paper, PaperFilter } from "./bindings";

const papers: Paper[] = await commands.listPapers({ year_min: 2024 });
```

Four design rules that make this work well:

1. **Narrow input structs per command.** Don't expose the raw `Query`
   AST across the IPC boundary — build small, typed `PaperFilter`-style
   structs. The frontend should never construct an `Expr` JSON tree.

2. **Hold heavy state server-side, pass IDs.** Mutation plans can be
   big. Park them in a `PlanStore` keyed by UUID, return a small
   `MutationPreview` to the frontend, accept the id back when the user
   confirms. See `examples/tauri_shape.rs` for the full pattern.

3. **`tauri::State<VaultState>` carries the vault.** One `Vault::with_root`
   call at app launch; commands borrow it. Add an mtime-validated cache
   on top of the parsed-record list when you want sub-millisecond
   queries.

4. **Wiki-link relations stay filter-only in v1.** Eager-load is the
   trap — you walk the whole graph for every list view. Keep
   `Paper::cites().any(…)` as a *filter*, fetch the related notes
   on-demand with `get_paper(name)` commands when the UI needs them.

## Safety properties inherited from core

- **Atomic writes.** Every mutation through `Update::execute` uses the
  underlying `UpdateBuilder`, which writes via tempfile + rename.
- **Vault lock.** Cross-process mutation serialisation comes for free
  from `vaultdb-core::lock`.
- **Plan/execute split.** `Update::plan()` is read-only. The Tauri
  pattern surfaces this directly: preview, then confirm.
- **Forced filter on bulk updates.** `Query::update()` returns an
  `Err` if the query has no user-supplied `.filter(…)` — the model
  discriminator is *not* enough to authorise touching every record.

## Status

Pre-1.0 alongside `vaultdb-core`. Public types are stable through the
v0.x series of `vaultdb-orm`; breaking changes bump the minor.
